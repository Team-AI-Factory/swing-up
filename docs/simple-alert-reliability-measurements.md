# Simple Alerts processing reliability

The cron response and bounded launcher summary now expose explicit processing and Committee counters. A transport-successful event job can still contain a failed required reviewer. Such a case stays queued with its immutable audit and partial token charges, but counts as a failed processing attempt and makes the cycle unhealthy. No approval, evidence, delivery, or spending gate is relaxed.

- `processingAttempts`: one non-idle event-job invocation. Each retry is a separate attempt; idle/busy probes and quiet cycles cannot dilute the denominator. A later error in the same invocation counts once.
- `processingFailures`: unsuccessful operations and technical analysis/reviewer failures, including an oversized final-judge request. Successful no-signal decisions and scheduled evidence/capacity deferrals are not technical processing failures.
- `committeeReviewAttempts`: conservatively admitted paid reviews, including partial calls and locally blocked required roles. This is not a count of completed assessments or provider invoice charges.
- `committeeTechnicalFailures`: reviews with failed or blocked required roles. Its separate rate prevents unrelated healthy source deferrals from diluting a high Committee failure rate.
- `committeeOutcomeUnknown`: an admitted review whose diagnostics do not establish completion or a known technical failure. Missing diagnostics cannot establish reliability.
- `nontechnicalDeferrals`: scheduled evidence/capacity retries without an identified processing failure. They remain unresolved work, not completed decisions.

Zero attempts produces a null rate, not a passing zero-percent result. Daily counters retain `processingMeasuredCycles` and `processingMeasurementStartedAt`; older cycles are not backfilled with invented successes. Daily totals alone do not prove two complete, non-overlapping 24-hour windows. Reconcile exact window logs, scheduled executions, unresolved cases, and receipt-backed decisions under the existing launch criteria. Source completeness, evidence latency, profile yield, delivery controls, cost headroom, and all expansion gates still require independent proof.

Regression coverage includes failed final judges with HTTP-successful retry results, valid incomplete-evidence/no-signal outcomes, idle exclusion, nonduplicated operation counts, unchanged cost reconciliation, no publication of failed reviews, legacy metric gaps, quiet-cycle accounting, and failed metric persistence.

## Evidence-preserving prompt-size repair

The public-equity runner places the same SEC receipt text in filing and news sections. Required roles also receive all earlier reviewer results, so a final judge can cross the 60,000-byte bound after earlier roles have completed. The prompt builder now gives repeated, exactly identical long text one complete verbatim definition in `sharedEvidenceTexts`. Each original field retains an explicit `verbatimTextRef` to that definition inside the same prompt. Role context, order, unique conditions, contradictions, prior reviewer results and source links are preserved. URLs remain directly in their original fields. No text is summarized or truncated, and near-duplicates are not merged. Existing reference-key collisions disable the transformation. A transformation is used only when it reduces bytes after accounting for the explanatory instruction.

The 60,000-byte gate, bounded model/output policy, shared $10 reservation accounting and final approval requirements remain unchanged. Unique oversized evidence still fails closed. A reference must never be interpreted as missing evidence or as an additional independent source.

A deterministic synthetic SEC fixture reproduces three successful reviewers followed by a 60,081-byte final-judge rejection. With readable exact-text references, the final prompt is 34,471 bytes; all four mock-provider roles complete, every serialized evidence value and previous result round-trips exactly, and the decision remains `needs_more_data`. This is controlled code verification, not proof that a live model will make an equivalent judgment.

The historical 3 October 2026 ON, VERI and JEF failures cannot be replayed exactly from accessible records. Railway logs retain event IDs, immutable audit keys, role failure statuses and partial token receipts, but deployed main recorded `providerFailure: null` for oversized input. The event-job audit stores the runner's report; that report omits the in-memory evidence pack, rendered messages and full earlier reviewer results. The pilot already records measured oversized prompt bytes, but exact historical messages cannot be recovered from those aggregate fields. Live pilot validation must therefore verify actual role completion, evidence/reference comprehension, unchanged publication gates and retained cost accounting before claiming the production failure resolved.

## Profile stream-failure accounting

A successful HTTP response header does not establish a readable annual filing. Profile requests now report body-stream errors back to the existing request counter. A timeout or transport failure while reading SEC submissions or annual-filing content increments `requestFailures` once and separately increments `responseBodyFailures`, without inventing another request. Both counters appear in the durable profile summary and bounded launcher summary.

HTTP errors and connection failures remain counted by the paced fetch wrapper and are not doubled. Missing business/customer prose, provider-budget deferrals before a network attempt, and deliberate cancellation after successful early extraction are not body transport failures. Evidence remains unverified when retrieval or extraction fails; no description is invented and no AI call is added. The regression exercises all of these cases using the actual cache and profile-builder code with in-memory storage and synthetic streams.

## Focused analyst output limit

The 3 October 2026 12:49 UTC AZZ review failed because the analyst reached its 900-token response limit (`finish_reason: length`). Its three other roles completed; all four responses remained cost-accounted, and the attempt was audited without approval or delivery. Exact response text was not retained in accessible logs, so the regression is representative rather than an exact replay.

The focused analyst now uses a strict JSON response schema with the existing required fields, exactly five findings and at most two entries in the other arrays. Compact wording targets 450 tokens and short references to source links that remain intact in the supplied evidence. The analyst can use the existing reserved ceiling of 1,000 output tokens; other role limits, model allowlist, call count, per-review reservation of $0.156 and shared $10 rolling limit are unchanged. Schema bytes are counted inside the 60,000-byte input gate, rather than added outside the reserved bound. The schema uses the [supported OpenAI Structured Outputs contract](https://developers.openai.com/api/docs/guides/structured-outputs) for the pinned GPT-4.1 mini model.

A truncated, filtered, refused or otherwise incomplete analyst response stays failed. Valid-looking JSON with a `length` finish reason cannot be approved. No JSON is closed or repaired, and no retry or extra paid call is introduced. Every reported token remains included in cost accounting. Schema rejection fails closed without silently falling back to a weaker format.

Synthetic tests cover the old 900-token cutoff versus the reserved 1,000-token ceiling, complete but non-approvable missing-evidence results, failed response accounting, refusal/filter handling, schema input bounds and unchanged budget admission. The evidence-reference regression now uses a five-finding fixture and a 25,900-byte repeated receipt: its final prompt falls from 60,926 to 35,516 bytes with an exact roundtrip. Live model completion and comprehension must still be observed before claiming the AZZ failure resolved.
